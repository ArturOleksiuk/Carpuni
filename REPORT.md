# Звіт до лабораторної роботи №2

## Тема роботи
Проєктування та розробка веб-додатку мовою TypeScript.

## Мета роботи
Навчитись проєктувати веб-додатки з використанням TypeScript, React, Express та MongoDB, а також реалізувати клієнт-серверний застосунок відповідно до заданого опису.

## Назва застосунку
`Carpuni` - університетська соціальна мережа у стилі Threads для студентів та викладачів.

## Постановка задачі
Необхідно було створити веб-додаток, у якому:

- доступ до системи отримують лише користувачі з університетської бази email;
- при реєстрації роль, факультет і група визначаються автоматично;
- головна сторінка містить таби `Стрічка` та `Події`;
- користувач може переглядати та публікувати пости;
- користувач може переглядати події та реєструватися на них;
- у профілі студента відображається розклад занять;
- адміністратор має окрему адмін-панель для модерації системи.

## Архітектура застосунку
Проєкт побудований як monorepo і складається з двох частин:

- `client` - клієнтська частина на React + TypeScript;
- `server` - серверна частина на Express + TypeScript.

Логіка роботи побудована за клієнт-серверною архітектурою:

1. Frontend відображає інтерфейс користувача.
2. Клієнт надсилає HTTP-запити до REST API.
3. Backend обробляє запити, виконує бізнес-логіку та працює з MongoDB.
4. Дані повертаються у frontend та зберігаються у Redux store.

## Структура бази даних
У проєкті використовується MongoDB. Реалізовано такі основні колекції:

- `users` - користувачі системи;
- `whitelistrecords` - дозволені університетські email;
- `posts` - пости у стрічці;
- `comments` - коментарі до постів;
- `events` - університетські події;
- `schedules` - розклад занять;
- `complaints` - скарги для модерації;
- `follows` - підписки між користувачами;
- `savedposts` - збережені пости;
- `notifications` - сповіщення;
- `conversations` і `messages` - моделі для повідомлень, підготовлені на рівні бекенду.

## Реалізований функціонал

### 1. Авторизація та реєстрація
- перевірка email через whitelist;
- реєстрація користувача тільки з дозволеною адресою;
- автоматичне визначення ролі, факультету та групи;
- збереження пароля у вигляді `bcrypt hash`;
- вхід користувача з генерацією `JWT token`;
- збереження сесії після оновлення сторінки.

### 2. Стрічка постів
- перегляд постів;
- створення нового поста;
- відображення автора, тексту, хештегів та часу публікації;
- лайки з оптимістичним оновленням інтерфейсу;
- перегляд кількості коментарів;
- відкриття списку коментарів під постом;
- додавання коментарів;
- видалення власних постів;
- видалення будь-яких постів адміністратором;
- збереження постів у вибране.

### 3. Події
- перегляд університетських подій;
- фільтрація подій;
- реєстрація на подію;
- скасування реєстрації;
- відображення кількості зареєстрованих користувачів.

### 4. Профіль користувача
- перегляд власного профілю;
- перегляд профілю іншого користувача;
- вкладка `Пости`;
- вкладка `Розклад`;
- вкладка `Збережені`;
- відображення реальної кількості підписників та підписок;
- перехід на профілі інших користувачів зі стрічки та списків.

### 5. Підписки
- підписка на інших користувачів;
- відписка від користувачів;
- окремі списки `Підписники` і `Підписки`;
- оптимістичне оновлення списків і лічильників.

### 6. Сповіщення
- отримання сповіщень при підписці та взаємодіях;
- сторінка зі списком сповіщень;
- позначення сповіщення як прочитаного.

### 7. Адмін-панель
- окремий інтерфейс для ролі `ADMIN`;
- відсутність звичайного профілю в адміністратора;
- перегляд реальних метрик системи;
- модерація скарг;
- видалення будь-яких постів у стрічці.

## Особливості реалізації

### Реальні дані замість mock-логіки
На початковому етапі проєкт працював на in-memory/mock даних, але згодом був переведений на MongoDB з використанням Mongoose. Це дозволило:

- реально зберігати користувачів, пости, події та інші сутності;
- зберігати стан після перезапуску клієнта;
- працювати з повноцінною базою даних;
- використовувати seed-дані для першого запуску.

### Оптимістичне оновлення UI
Для зменшення затримок в інтерфейсі було реалізовано оптимістичні оновлення:

- лайків;
- створення постів;
- реєстрації на події;
- підписок/відписок;
- додавання коментарів;
- адміністративних дій.

Це дозволило зробити інтерфейс швидшим і зручнішим для користувача.

### Захист доступу
У серверній частині використано JWT-автентифікацію. Для адміністративних маршрутів реалізовано перевірку ролі користувача, завдяки чому функції модерації доступні лише адміністратору.

## Приклади ролей у системі
У застосунку використовуються такі ролі:

- `STUDENT`
- `TEACHER`
- `MODERATOR`
- `ADMIN`

Роль визначається автоматично на основі запису у whitelist.

## Що було реалізовано відповідно до завдання
Відповідно до опису з лабораторної роботи в застосунку реалізовано:

- сторінку авторизації;
- перевірку університетського email;
- автоматичне визначення ролі;
- головну сторінку з табами `Стрічка` і `Події`;
- профіль користувача;
- відображення розкладу;
- адмін-панель;
- модульну клієнт-серверну архітектуру;
- використання TypeScript у frontend і backend;
- використання MongoDB як бази даних.

## Результат роботи
У ході виконання лабораторної роботи було розроблено повноцінний прототип веб-застосунку `Carpuni`, який реалізує основні можливості університетської соціальної мережі. Застосунок має frontend і backend частини, використовує TypeScript на всіх рівнях, працює з MongoDB та підтримує ролі користувачів.

Розроблений проєкт демонструє:

- використання сучасного стеку веб-розробки;
- побудову REST API;
- роботу з документною базою даних;
- організацію глобального стану на клієнті;
- реалізацію авторизації та ролей;
- інтеграцію клієнтської та серверної логіки.
